# Zen Cart v19 migration evidence

## Source and support decision

The appliance installs the official Zen Cart v2.2.2 tag. Debian 13 does not
package the Zen Cart application, so the upstream release archive is the
primary application source while PHP, Apache, MariaDB, Postfix, and supporting
tools come from Debian.

- Tag: `v2.2.2`
- Tag commit: `63cf0ec3324d49767d25a07d168cdecb829e4d2a`
- Archive SHA256: `5fdb86e97460975b5f7a5e25affd3616b2470b96001aa3f1192bd0cc4c0efadc`
- Upstream compatibility: PHP 8.2 through 8.5, MariaDB 10.2.7 or later, and Apache
- Security contact: `security@zen-cart.com`

The build downloads the exact tag archive and rejects a digest mismatch. The
installed source record retains the tag commit, archive digest, version, and
update channel for runtime checks.

## Acceptance crosswalk

| Appliance contract | `tests/v19.sh` evidence |
| --- | --- |
| Storefront | Loads the configured HTTPS storefront and identifies Zen Cart. |
| Administrator access | Logs in at `/manage/login.php` with the CSRF token and reaches authenticated server information. |
| Product write and read | Creates a disposable category, submits a product through the authenticated administrator flow, checks MariaDB persistence, and reads the product from the storefront. |
| Database | Requires a responsive MariaDB service and verifies the product rows. |
| Web server | Requires a valid Apache configuration and the enabled Zen Cart virtual host. |
| Mail | Requires loopback-only Postfix and submits a local application message. |
| Updater | Checks the official v2.2 patch channel, binds the candidate tag commit and archive digest, and proves the apply plan with a dry run. |
| TurnKey platform surfaces | Core supplies SSH, Adminer, Webmin, TLS, backups, and first-boot integration. The application test covers the Zen Cart boundaries added by this appliance. |

The runtime test emits exactly the seven Wave 2 result keys: package source,
installed version, runtime checks, updater command, updater result, updater
channel, and integrity evidence.

## Candidate status

The candidate passes Bash syntax, Python byte-compilation, Git whitespace,
executable-mode, exact seven-key result-schema, official tag-resolution, and
archive-digest checks. The official tag resolves to the recorded commit and the
downloaded archive hashes to the recorded SHA-256. The exact Wave 2 runtime is
queued while the shared TKLDev builder is restored; run it with:

```bash
tools/test-v19-appliance zencart --source /path/to/clean/zencart/worktree
```

Product-fix accounting is 2 of 2. The preserved candidate's runtime test used
the build-time administrator password instead of the throwaway password set by
the exact harness during first boot. The test now reads `TKL_TEST_APP_PASS`,
which keeps its login assertion bound to the credential actually configured by
the harness. The first exact build then showed that the installer rejected a
successful `ajaxAdminSetup.php` response because Zen Cart omits the optional
`error` field on success. The installer now rejects only an explicit error and
requires the expected unchanged administrator-directory response. Earlier
Docker storage and runner-availability failures were infrastructure evidence
and did not consume a product-fix loop.

## Deferred issues

- MEDIUM: `turnkey-zencart-update` intentionally follows only v2.2 patch
  releases. Major or minor upgrades can include database and customization
  changes, so they remain a supervised workflow using the official upgrade
  documentation.
- LOW: Acceptance uses the real HTTP administrator and storefront flows with
  CSRF and session handling, but does not add full browser automation.
